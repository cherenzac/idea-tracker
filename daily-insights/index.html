Worked example: same data, different order

Start at c = 0. For each observation x, update c to (c + x) / 2. Move the value 12 through three zeros. Evaluate each final estimate on the same four observations:

  • 12 first: final estimate 0.75, mean squared error 32.0625.
  • 12 second: final estimate 1.5, mean squared error 29.25.
  • 12 third: final estimate 3, mean squared error 27.
  • 12 last: final estimate 6, mean squared error 36.

The arithmetic mean is 3 in all four orders. On this fixed sample, mean squared error at any estimate c is 27 + (c − 3)². That explains the batch baseline without assuming it will generalize to a changing stream.

This is a one-centroid, fixed-step illustration with no reassignment. It is not an implementation or benchmark of e-means, which uses a different update and discusses centroid finalization.

Worked example: one late order, two answer keys

In this fictional warehouse, three Q1 orders are visible before April 2. A fourth order, placed March 29, arrives April 3. An April 1 order is already visible but falls outside Q1. To check the counts, filter ordered_on to January 1 inclusive through April 1 exclusive, then filter ingested_on to earlier than the snapshot cutoff.

  • Fresh April 4 query: 4. A fixed key of 3 marks this wrong; the April 4 reference correctly passes it.
  • Stale April 2 cache: 3. A fixed key of 3 marks this right; the April 4 reference correctly fails it.
What the evaluation harness should record

For regression tests, run both versions on the same frozen snapshot and metric definition. For live evaluations, record the intended and observed snapshot versions separately, along with the metric version and authorized data scope. Run an independent reference query against the intended snapshot. If that snapshot cannot be recovered, leave the answer unscored and record the missing evidence; do not count it as model drift.

A timestamp is not a snapshot ID: backfills and corrections can change results even when a query uses the same date filter. This example illustrates a test design, not a claim about a shipping dbt feature.

Worked example: when does a retrieval index pay off?

Suppose a plain scan costs 2,000 compute units per query, while indexed lookup costs 400 after a 48,000-unit build. For q queries on one index version, compare 2000 × q with 48000 + 400 × q.

  • 20 queries: scan 40,000; index 56,000. Scanning uses less compute.
  • 30 queries: both cost 60,000.
  • 31 queries: scan 62,000; index 60,400. This is the first strict win for the index.

At 40 queries, one build costs 64,000 units. If a document update forces a full rebuild halfway through, two builds cost 112,000. The same 40 queries cost 80,000 by scanning either way. In production, use measured build and update costs rather than assuming every update requires a rebuild.

This fictional model compares total compute, not latency or retrieval quality. Before switching, check recall against a reference, verify access rules still hold, and measure tail latency, freshness and storage separately. A cheaper index is not a reason to serve content a caller cannot access.

Worked example: tune the existing graph first

In this fictional comparison, freeze the corpus, embeddings, distance metric and tie rule. For each of 100 held-out queries, compute the exact top 10. Recall@10 is the fraction of those 1,000 reference neighbors returned. Require at least 95% recall and keep the hardware and query concurrency fixed.

  • Existing graph, ef=20: 920 neighbors returned, 92% recall, 3 ms p95. This setting misses the floor.
  • Existing graph, ef=64: 960 neighbors returned, 96% recall, 6 ms p95.
  • Rebuilt graph, ef=48: 960 neighbors returned, 96% recall, 4 ms p95.

The comparison is 6 ms versus 4 ms, not 3 ms versus 4 ms. First sweep query settings on each fixed graph using a validation set, then report the winning settings on held-out queries. In hnswlib’s parameter guide, ef changes search effort at query time; changing graph-build parameters such as M or ef_construction for the existing corpus means building a new graph.

These are invented measurements, not an HNSW benchmark. Check recall on important query slices, index size, and separate build cost. The p95 difference is a latency result, not a per-query compute saving. Neighbor recall does not measure whether the final answer is correct or whether the user can access the source.
